# ADR-0004 · Skill Registry runtime exposure

> **Status**: Accepted (2026-05-17 · Wave-200 Phase 2)
> **Decision drivers**: 1,423-skill library is the operator's compounding asset · runtime exposure beats per-prompt context bloat · Mastra agent must inherit existing recall layer unchanged

---

## Context

The operator has 1,423 skills installed under `~/.claude/skills/` (sourced
from Anthropic, internal authors, and external libraries like
superpowers-lab). Each skill is a self-contained `SKILL.md` with progressive
disclosure: short YAML frontmatter (name + description), then a body that
may include scripts, references, and assets.

Two failure modes for using a library this large:

1. **Naive load**: inline every SKILL.md into the system prompt. Cost: 1,423
   skills × ~600 tokens average ≈ **854K tokens per turn** — would
   exhaust any model's context window before a reply could fire. Discarded
   immediately.

2. **Static curation only**: hard-code the top-N most useful skills (we
   keep the top-50 always-on floor in `~/.claude/CLAUDE.md`). Problem: the
   long tail (~1,373 skills) becomes dead weight — installed but unreachable
   at runtime. The operator loses the compounding library value.

Wave-200 Phase 1 shipped Nick as a real Mastra agent with the full
`nourTools` catalog (138 tools). Phase 2 was originally spec'd as "wire up
Anthropic Tool Search Tool over skill registry". On audit, that work was
**already shipped at the app layer** in v10.0.431-434 — the question
became "is the existing layer enough, or do we need to swap it out for
the Anthropic-native Tool Search Tool surface?"

## Decision

**Keep the existing recall layer. Don't swap in Anthropic Tool Search Tool.**
The existing implementation already gives us the 85% context reduction
benefit, and it works across providers (Venice / Ollama / Anthropic /
OpenAI) — Anthropic's Tool Search Tool is single-vendor.

The recall layer (already shipped) is composed of three pieces:

### 1 · Indexed registry · `data/skills-registry.json`

11,279 lines. One JSON document with `{ generatedAt, totalSkills, skills[] }`.
Each skill entry: `{ name, description, category, tags, source, risk,
path }`. Generated by `scripts/build-skills-registry.ts` (re-runnable when
new skills are installed) and `scripts/embed-skills.ts` (writes one
`VectorEmbedding` row per skill with `sourceType="skill"`).

### 2 · Recall function · `lib/skills/skill-recall.ts`

Two entry points:
- `recallSkills(query, topK)` · embedding-based semantic search over the
  registry. Cosine similarity in JS · 60-90ms per query · returns top-K
  matches with `{ name, description, similarity, category, tags, path }`.
- `recallSkillsByCategory(category, limit)` · enumerator for explicit
  domain lookup ("show me content skills") · no embedding cost.

Cosine floor: 0.30 · top-K hard cap: 10 · query embedding cached 60s.

### 3 · System-prompt injector · `lib/skills/skill-context.ts`

`getRelevantSkillsBlock(userMessage)` — fires during prompt assembly,
returns a compact ≤3-skill block with similarity scores + usage hint
("if one of these protocols cleanly fits, apply it · use searchSkills
to widen"). Hard-fails closed (empty string) on any error so a recall
failure never breaks the chat path. Telemetry: writes one
`SystemMetric` row per recall with `metric="skill.recall.injected"`
for future correlation against judge-eval scores.

### Mastra inheritance · automatic

When `getNickAgent()` constructs the Mastra Agent (`src/mastra/agents/nick.ts`),
it passes `tools: nourTools as never`. `nourTools` is the barrel at
`lib/ai/tools.ts` that spreads `brainTools` (23 tools) into the agent
surface. `brainTools.searchSkills` is the explicit runtime lookup tool —
it's exactly the same tool the legacy chat surface already uses.

**Result**: zero new code needed for Phase 2 substrate. Nick-as-Mastra-agent
inherits the recall layer the moment Phase 1's flag flips on.

## Rejected alternatives

### Anthropic Tool Search Tool (native)

Per Anthropic's Claude 4 docs, Tool Search Tool gives an 85% context
reduction by deferring tool schemas until the model requests them. The
model sees only tool names in the initial prompt; it loads schemas via
`tool_search` calls.

Why we don't adopt it:
- **Single-vendor lock-in** · the wrapper only fires when Anthropic is
  the active provider. Our provider chain (Venice → Ollama → Anthropic →
  OpenAI) means most calls don't hit Anthropic. Adopting Tool Search
  Tool would split behavior across providers.
- **The 85% saving is for tool schemas, not skill bodies** · we're
  already paying ~0 cost on skill bodies (we don't inline them). The
  saving is real but solves a different problem.
- **Reversibility cost** · once tools are behind Tool Search Tool, we'd
  need a 2-path tool registration system to remain provider-agnostic.
  Not worth the maintenance burden.

If a Anthropic-only deploy ever becomes the target, we can add Tool
Search Tool as a wrapper around the existing `nourTools` map without
touching the recall layer. Leaves the door open.

### Per-surface skill bundles

E.g. "the morning brief workflow gets a hand-picked 10-skill subset · the
chat surface gets a different 12-skill subset". Tried in prior waves
(Wave-150). Discarded because:
- Drifts immediately as skills are added · maintenance burden compounds
- The operator names skills by category in conversation ("content skills" ·
  "design skills") · per-surface bundles can't satisfy that ask
- Duplicates the work the recall layer already does for free

### Mem0-style memory layer for skills

Mem0 / Letta could store skill-usage telemetry and learn which skills
correlate with which task types. Real value, but **layered on top** of
the recall layer, not a replacement. Punted to Phase 6 (predictive
brain) where Mem0 lands for customer/operator preferences anyway.

## Consequences

### Positive

- **Zero code shipped for Phase 2** · the recall layer Phase 1 inherits
  is already production-tested across hundreds of chat turns
- **Provider-agnostic** · same behavior on Venice, Ollama, Anthropic,
  OpenAI · no vendor lock
- **Telemetry already wired** · `SystemMetric` rows let us correlate
  skill recall with judge-eval scores (Phase 1.2 quarterly re-curation)
- **Bottleneck moved to skill curation** · the bottleneck is now
  "are the right skills installed + indexed", not "can the agent find
  them at runtime". That's the right place for the bottleneck to be.

### Negative

- **Recall quality depends on `description` text quality** · skills with
  weak/generic descriptions are unreachable. Mitigated by
  `scripts/translate-skill-descriptions.ts` which rewrites bad ones to
  English-summary form during registry build.
- **No per-skill version pinning** · the registry rebuild picks up the
  latest version of every skill. A regression in a skill description
  could shift recall results silently. Acceptable for now · revisit if
  it ever causes a measurable regression in the Braintrust eval suite.

### Neutral

- **Anthropic Tool Search Tool is still available** · documented as a
  future wrapper if Anthropic becomes the dominant provider

## Operator action items

None. This ADR documents the as-built. Future re-indexing happens via:

```bash
pnpm tsx scripts/build-skills-registry.ts   # re-scan ~/.claude/skills/
pnpm tsx scripts/embed-skills.ts            # re-embed any new skills
```

The recall layer picks up changes automatically · no deploy needed
(registry is read at runtime with a 1-hour cache).
