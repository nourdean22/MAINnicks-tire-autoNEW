## SECTION: Next.js 16 — middleware.ts vs proxy.ts (P0 question) + security releases

**Source (first-party):** https://nextjs.org/docs/messages/middleware-to-proxy (accessed 2026-09-02)
> "You are using the `middleware` file convention, which is deprecated and has been renamed to `proxy`... The `middleware.ts` file is still available for Edge runtime use cases, but it is deprecated and will be removed in a future version." (quote of the note is from the next-16 blog post, corroborated on this docs page)

**Source (first-party):** https://nextjs.org/blog/next-16 (published October 21st 2025, accessed 2026-09-02)
> "`proxy.ts` (formerly `middleware.ts`)... `proxy.ts` replaces `middleware.ts` and makes the app's network boundary explicit. `proxy.ts` runs on the Node.js runtime... **What to do**: Rename `middleware.ts` → `proxy.ts` and rename the exported function to `proxy`. Logic stays the same... **Note:** The `middleware.ts` file is still available for Edge runtime use cases, but it is deprecated and will be removed in a future version."

**ANSWER to the P0 question:** Next.js 16 does **NOT** ignore a root `middleware.ts` — it still honors it and runs it (on the Edge runtime), so StateNour's existing auth boundary in `middleware.ts` continues to function on 16.2.11. This is **not an outage-class P0**, but it **is a live deprecation**: Next.js explicitly states `middleware.ts` "will be removed in a future version" (no removal version/date committed yet in the source). Official migration path is the codemod `npx @next/codemod@canary middleware-to-proxy .`, which renames the file and the exported function (`middleware` → `proxy`); the new `proxy.ts` convention runs on the **Node.js runtime** (not Edge), which is itself a runtime-semantics change worth testing (any Edge-runtime-only APIs currently used in `middleware.ts` need review before renaming). Recommendation: migrate proactively on a branch since removal timing is unannounced but explicit.

## SECTION: Model Context Protocol (spec + SDK + security) — Q1

**Current spec version:** **2026-07-28**, confirmed finalized/stable as of access date.
- Source: https://modelcontextprotocol.io/specification (accessed 2026-09-02) — the canonical `/specification` index now points at `schema/2026-07-28/schema.ts` as "the authoritative protocol requirements," with no release-candidate framing left on that page.
- Source: https://blog.modelcontextprotocol.io/posts/2026-07-28-release-candidate/ (accessed 2026-09-02) — "The release candidate is locked as of May 21, 2026. The final specification will be published on July 28, 2026." Today (2026-09-02) is after that date, consistent with the spec index now showing 2026-07-28 as current, non-RC.
- Previous stable was **2025-11-25** (source: https://modelcontextprotocol.io/specification/2026-07-28/changelog, accessed 2026-09-02, which opens "This document lists changes made to the Model Context Protocol (MCP) specification since the previous revision, 2025-11-25").

**What changed 2025-11-25 -> 2026-07-28** (source: the changelog page above — MCP's own blog calls this "the largest revision of the protocol since launch"):
- **Stateless sessions / Streamable HTTP overhaul:** protocol-level sessions and the `Mcp-Session-Id` header are removed from Streamable HTTP; `tools/list`/`resources/list`/`prompts/list` no longer vary per-connection. The `initialize`/`notifications/initialized` handshake is removed entirely — every request now carries protocol version + client capabilities in `_meta`, and a new mandatory `server/discover` RPC advertises server capabilities/identity up front.
- **SSE resumability removed:** `Last-Event-ID` / SSE event-ID based stream resumption is dropped from Streamable HTTP — a broken stream now means the client re-issues the request with a new request ID rather than resuming.
- **HTTP+SSE transport** (deprecated since spec version 2025-03-26) is now formally reclassified **Deprecated** under a new feature-lifecycle policy (Active -> Deprecated -> Removed, minimum 12-month deprecation window) — confirms Streamable HTTP is the only forward path.
- **Tasks** moved out of core into an official extension (`io.modelcontextprotocol/tasks`) for long-running/async work: polling via `tasks/get`, mid-flight input via `tasks/update`, unsolicited task handles allowed.
- **Elicitation** changed: the `notifications/elicitation/complete` notification and `elicitationId` (both introduced in 2025-11-25) are removed; elicitation now goes through the new **Multi Round-Trip Requests (MRTR)** pattern — a server returns `resultType: "input_required"` with `inputRequests`, and the client retries the original request with `inputResponses`. This same MRTR pattern also replaces server-initiated `roots/list` and `sampling/createMessage`.
- **Structured tool output:** `inputSchema`/`outputSchema` loosened to allow any JSON Schema 2020-12 keyword; `structuredContent` now allows any JSON value (previously more restrictive).
- **Extensions framework:** new `extensions` field on `ClientCapabilities`/`ServerCapabilities` formalizes optional, opt-in functionality beyond core protocol (Tasks, "Skills over MCP", and "MCP Apps" — interactive inline UI — are called out as notable extensions).
- **Sampling, Roots, and Logging are deprecated** (SEP-2577): still functional during the deprecation window, but new implementations should not adopt them. Suggested replacements: pass files/dirs via tool params instead of Roots; call LLM provider APIs directly instead of Sampling; use stderr/OpenTelemetry instead of the Logging capability.
- **OAuth 2.1 / authorization hardening:** authorization servers SHOULD include `iss` per RFC 9207 and clients MUST validate it (mix-up attack defense); Dynamic Client Registration (RFC 7591) is deprecated in favor of **Client ID Metadata Documents (CIMD)** as the preferred client-registration path (DCR kept only for back-compat); client credentials are now bound to the issuing authorization server (must key by issuer, must not reuse across servers).
- **Caching hints:** new `CacheableResult` interface requires `ttlMs` + `cacheScope` (`public`/`private`) on list/read results.
- **Error-code allocation policy:** JSON-RPC server-error range partitioned — `-32000..-32019` stays implementation-defined (grandfathered), `-32020..-32099` reserved for MCP; several draft-era codes renumbered into that band.

**SDK implementing the current spec:** A new **TypeScript SDK v2** line (separate, focused packages — `@modelcontextprotocol/server`, `@modelcontextprotocol/client`, `@modelcontextprotocol/core`, framework adapters like `@modelcontextprotocol/express`/`fastify`/`hono`/`node`, plus `@modelcontextprotocol/codemod`) implements 2026-07-28. Source: https://blog.modelcontextprotocol.io/posts/sdk-betas-2026-07-28/ (published June 29, 2026, accessed 2026-09-02) — "TypeScript v2 retires the monolithic `@modelcontextprotocol/sdk` package in favor of focused ones," and "once v2 ships, the TypeScript SDK will continue shipping v1.x bug fixes and security updates for at least six months."

**What StateNour's pin targets:** `@modelcontextprotocol/sdk` is the **v1.x monolithic package**; latest v1.x is **1.30.0** (StateNour pins **1.29.0**, one patch behind latest-of-line). Source: https://www.npmjs.com/package/@modelcontextprotocol/sdk dist-tags (accessed 2026-09-02) shows `"latest": "1.30.0"` — note `dist-tags.latest` on this package now points at the newest 1.x release, not the v2 packages, since v2 shipped under new package names rather than as `@modelcontextprotocol/sdk@2.x`. Per the v2 migration doc (https://github.com/modelcontextprotocol/typescript-sdk/blob/main/docs/migration/support-2026-07-28.md, accessed 2026-09-02), the v1.x line is built around what that doc calls the "2025-era protocol versions (2024-10-07 to 2025-11-25)" `initialize`-handshake model. The exact `LATEST_PROTOCOL_VERSION` constant shipped specifically in the 1.29.0 tag could **not** be directly confirmed (GitHub raw file fetch for that tag 404'd; npm's per-version page returned 403) — so treat this as a well-supported inference, not a directly-confirmed fact: 1.29.0/1.30.0 top out at protocol revision **2025-11-25** and do NOT implement the stateless 2026-07-28 redesign (no `server/discover`, no MRTR, still uses the removed `initialize` handshake and `Mcp-Session-Id`). Moving to 2026-07-28 semantics requires migrating off `@modelcontextprotocol/sdk` entirely onto the v2 packages — this is a **package-name-level breaking migration**, not a version bump.

**Official security guidance** — source: https://modelcontextprotocol.io/docs/tutorials/security/security_best_practices (accessed 2026-09-02, cross-linked throughout to `/specification/2026-07-28/...`, so current as of the 2026-07-28 spec):
- **Confused deputy problem:** MCP proxy servers that use a static `client_id` against a third-party authorization server, combined with dynamic client registration for MCP clients and a consent cookie set by the third party, let an attacker skip consent and redirect a stolen authorization code to an attacker-controlled `redirect_uri`. Mitigation (MUST): per-client consent tracked server-side *before* forwarding to the third-party authorization server, `__Host-`-prefixed/`Secure`/`HttpOnly`/`SameSite=Lax` consent cookies bound to `client_id`, exact-match `redirect_uri` validation, and cryptographically random single-use OAuth `state` set only after consent approval.
- **Token passthrough (explicitly forbidden anti-pattern):** "MCP servers MUST NOT accept any tokens that were not explicitly issued for the MCP server." Accepting/forwarding tokens whose audience wasn't the MCP server breaks OAuth's trust boundary, defeats downstream rate-limiting/audit controls, and re-creates the confused-deputy problem one layer down.
- **Prompt injection:** not a single named top-level section the way confused-deputy/token-passthrough are (this doc's named attack sections are: Confused Deputy, Token Passthrough, SSRF, State Handle Hijacking, Local MCP Server Compromise, OAuth Authorization URL Validation/XSS/RCE, stdio Transport Security in Proxy Scenarios, Mix-Up Attacks, Localhost Redirect URI Impersonation, CIMD Trust Policies, Scope Minimization) — general prompt-injection guidance instead lives in the protocol's overall Security and Trust & Safety principles at https://modelcontextprotocol.io/specification (same access date): "descriptions of tool behavior such as annotations should be considered untrusted, unless obtained from a trusted server," and hosts "must obtain explicit user consent before invoking any tool."
- Newer 2026-07-28-specific attack classes also documented on that same security-best-practices page: **State Handle Hijacking** (now-stateless MCP mints server-side handles instead of sessions; servers MUST NOT treat possession of a handle as authentication, MUST bind handles to the authenticated user server-side), and **SSRF during OAuth metadata discovery** (a malicious server points `resource_metadata`/`authorization_servers`/`token_endpoint` URLs at internal IPs or cloud metadata endpoints like `169.254.169.254`; clients SHOULD block private/reserved IP ranges per RFC 9728 section 7.7 and enforce HTTPS).

## SECTION: Inngest — Q6 (throttle vs rateLimit, realtime, Next.js 16)

**Throttle vs rateLimit semantics** (first-party, both accessed 2026-09-02):
- `rateLimit` — source: https://www.inngest.com/docs/guides/rate-limiting — **is lossy**: "Events that exceed the rate limit are skipped and do not trigger functions to start." The doc explicitly warns: "Any events received in excess of your limit are ignored. This means this is not the right approach if you need to process every single event sent to Inngest. Consider using throttle instead."
- `throttle` — source: https://www.inngest.com/docs/guides/throttling — **is non-lossy / queuing**: "When the limit is reached, new function runs over the throttling limit will be enqueued for the future," processed FIFO as capacity frees up.
- **Implication for StateNour:** anywhere `rateLimit` is used on a function that must not silently drop work (e.g. a webhook receiver, a billing/critical-notification path), that is a correctness bug by design, not a bug in Inngest — `throttle` is the correct primitive when every invocation must eventually run.

**Realtime API status:** first-class, current feature — source: https://www.inngest.com/docs/features/realtime and https://www.inngest.com/docs/features/realtime/react-hooks (accessed 2026-09-02). Provides channels/topics and a `useRealtime` React hook to stream progress/results from long-running functions directly into UI components; the Next.js quick-start doc was last updated June 16, 2026 per search indexing, consistent with active maintenance.

**Next.js 16 compatibility:** Inngest documents first-class support for both the Next.js App Router and Pages Router API-route serving model; no incompatibility with Next.js 16 specifically was found in first-party docs. **NOT VERIFIED**: an explicit first-party statement of Next.js-16-specific compatibility (e.g., a changelog line naming "16") was not located — the support claim is inferred from the general "first class support for Next.js" framing plus a June 2026 doc-freshness signal, not a version-pinned compatibility statement. On serverless/Railway-style deployments, Inngest's own guidance (SDK v4 docs) recommends configuring `maxRuntime` on the Inngest client and `maxDuration` on the `/api/inngest` route to avoid platform timeout issues — directly relevant given Railway's own request-duration ceiling (see Railway section below).

## SECTION: Railway — Q7 (healthcheck, maxDuration, streaming timeouts)

**Healthcheck behavior** — source: https://docs.railway.com/guides/healthchecks (accessed 2026-09-02):
- Default healthcheck timeout: **300 seconds (5 minutes)**, configurable per-service.
- UI caps the field at 999 seconds, but the `RAILWAY_HEALTHCHECK_TIMEOUT_SEC` service variable can raise it further (community/help-center sources reference up to 3600s via the variable — this specific ceiling is community-sourced, not confirmed on the first-party guide page itself, so treat the 3600s figure as **NOT VERIFIED** at first-party level even though the 300s default and 999s UI cap are confirmed first-party).
- Railway explicitly does **not** monitor the healthcheck endpoint after a deployment goes live — healthchecks only gate deploy promotion, not steady-state traffic.

**Route `maxDuration` — is it inert on Railway?** Next.js's own docs (https://nextjs.org/docs/app/api-reference/file-conventions/route-segment-config/maxDuration, accessed 2026-09-02, page metadata shows `version: 16.3.4`, `lastUpdated: 2026-03-13`) say only: "Deployment platforms can use `maxDuration` from the Next.js build output to add specific execution limits" — i.e., `maxDuration` is a hint Next.js emits in its build output; enforcement is entirely up to the hosting platform choosing to read and act on it. Vercel is the platform documented to consume it (https://vercel.com/docs/functions/configuring-functions/duration). **Railway does not build on Vercel's build-output-API function runtime** — it runs the Next.js server as a long-lived Node process behind Railway's own proxy — so there is no first-party Railway documentation of it reading/enforcing `maxDuration` at all. **Verdict: effectively inert on Railway** (well-supported inference from how the two platforms differ, not a direct "Railway ignores maxDuration" statement from either vendor — flagged as inference, not a directly-quoted confirmation). What actually governs request lifetime on Railway is the platform's own proxy-level timeout below, independent of anything in the Next.js route file.

**Actual request-timeout ceiling on Railway** — source: https://docs.railway.com/networking/public-networking/specs-and-limits (accessed 2026-09-02), quoted verbatim:
- "HTTP requests can run for up to 15 minutes if data keeps transferring (for example, keep-alive heartbeats), and are otherwise closed after 5 minutes with no data transferred."
- "Request bodies must finish uploading within 5 minutes."
- "Idle HTTP/1.1 connections are closed after 60 seconds between requests."
- "Websocket connections are exempt from these duration and inactivity limits, and can stay open indefinitely, even while idle."
- Max 32 KB combined header size; 10,000 concurrent connections; ~11,000 requests/sec/domain; 10,000 requests per connection.
- **Direct implication for StateNour's AI streaming routes** (`ai` SDK `streamText`/agent responses, potentially long LLM generations): as long as the stream keeps emitting bytes, Railway allows up to **15 minutes**; but any request that goes silent (e.g., a stalled upstream model call, a long non-streaming tool-call round-trip with no bytes flushed to the client) for more than **5 minutes with zero data transferred** will be hard-closed by Railway's proxy regardless of what `maxDuration` says in the route file. Recommend auditing any StateNour route that can go >5 minutes without flushing a byte (e.g., waiting on E2B/Firecrawl/Stagehand tool calls before streaming a token) — these are the routes actually at risk, not simple long streams.

## SECTION: Neon — Q8 (autosuspend, poll cost, read-only-on-quota)

**Autosuspend / scale-to-zero** — source: https://neon.com/docs/introduction/scale-to-zero (accessed 2026-09-02): Neon suspends a compute after a period of inactivity — default **5 minutes** — to minimize cost; the compute resumes transparently on the next connection/query.

**Cost implication of a 15-minute poll:** confirmed mechanism, source: https://neon.com/docs/guides/consumption-limits (accessed 2026-09-02) — Neon meters and bills on `active_time_seconds`, "total cumulative usage across all branches and computes in a given project" through the billing period. A poller that hits the database every 15 minutes keeps re-triggering compute resume and, more importantly, if the poll cadence is shorter than the autosuspend inactivity window (5 min default), it **prevents the compute from ever reaching the idle threshold**, i.e., the compute stays continuously active instead of scaling to zero between polls — directly increasing `active_time_seconds` billed. This exact failure mode is what the operator's own memory log (statenour-neon-readonly-and-ingest-reviews-2026-08-19, 2026-08-19) already root-caused in production: a worker polling `/api/sync/queue/render` every 2 minutes kept the compute 97% active, which is the same class of problem a 15-minute poll would cause at a lower but still nonzero severity — any poll interval shorter than the autosuspend window defeats scale-to-zero economics.

**Read-only mode on quota (PG 25006):** this is a **two-mechanism story**, confirmed first-party:
1. Ordinary SQLSTATE 25006 ("cannot execute ... in a read-only transaction") — source: https://neon.com/docs/connect/connection-errors (accessed 2026-09-02) — is generic Postgres behavior with three causes unrelated to Neon billing: connected to a **read replica** (runs on a compute "in recovery," forcing every transaction read-only), a session/transaction explicitly set read-only (`BEGIN TRANSACTION READ ONLY`, `SET default_transaction_read_only = on`), or a **pooled connection that inherited a read-only setting** from a prior client that didn't reset it before the connection returned to the pool.
2. **Quota-triggered suspension** — source: https://neon.com/docs/guides/consumption-limits (accessed 2026-09-02) — is a distinct, harsher mechanism: "when a project hits a quota, Neon suspends its computes" — this is a **full compute suspension, not merely read-only**, and critically "this suspend will not restart at the next API call or incoming connection" (unlike normal scale-to-zero, which resumes transparently). A quota-suspended project stays down until the next billing period or until an operator raises/removes the limit (setting the quota to 0 removes it). Free-plan projects specifically: "the project's compute is suspended until the next billing period or until you upgrade, and existing connections drop and new ones can't open."
- **Net assessment:** the operator's memory log describes writes "silently no-oped" under PG 25006 during a quota lock — this is consistent with app code that doesn't distinguish "compute fully suspended" from "transaction is read-only" and simply swallows the resulting Postgres error; the underlying Neon mechanism is full suspension (mechanism 2), not a partial read-only degrade mode. Recommend the app's error handling explicitly detect quota-suspension (vs. ordinary 25006) and alert loudly rather than silently no-op, since mechanism 2 does not self-heal on next connection the way normal autosuspend does.

- **Tool calling / streaming lifecycle renamed wholesale:** `system` -> `instructions`; system messages inside `prompt`/`messages` arrays now rejected by default unless `allowSystemInMessages: true`; `onFinish` -> `onEnd`, `onStepFinish` -> `onStepEnd`, `experimental_onStart` -> `onStart`, `experimental_onStepStart` -> `onStepStart`; tool execution callbacks `experimental_onToolCallStart`/`Finish` -> `onToolExecutionStart`/`onToolExecutionEnd`; `needsApproval` deprecated in favor of a `toolApproval` config option; `experimental_context` -> `context`, with shared runtime data moved to a new `runtimeContext`.
- **Streaming wire/result shape:** `fullStream` renamed to `stream` on `streamText` results; request/response bodies now excluded from results by default (opt in via `include`); step response messages no longer auto-accumulated — use top-level `result.responseMessages`.
- **Structured output:** `experimental_output` removed, replaced by stable `output`; `CallSettings` type split into `LanguageModelCallOptions` and `RequestOptions`. `generateObject`/`streamObject` remain deprecated (per the 6.0 guide) in favor of `generateText`/`streamText` with an `output` setting — this deprecation, introduced in 6.0, carries forward into 7.0.
- **Multi-step usage tracking:** `usage` now reflects **totals across all steps** rather than just the final step; `totalUsage` is deprecated (the meaning of `usage` itself changed — a silent behavior change if StateNour reads `usage` anywhere expecting final-step-only numbers).
- **Telemetry:** OpenTelemetry integration moved out of core into a separate `@ai-sdk/otel` package; the `experimental_telemetry` option is now stable `telemetry`; telemetry is enabled by default once an `@ai-sdk/otel` integration is registered (no more explicit `isEnabled: true`) — **relevant to StateNour's own `@opentelemetry/sdk-node` + `@langfuse/otel` stack**, since upgrading to AI SDK 7 would require adding `@ai-sdk/otel` and re-registering telemetry globally.
- **Agent / loop abstractions (new in 7, expands on 6's `ToolLoopAgent`):** two first-class classes — **`ToolLoopAgent`** (agentic loops with tool approvals, typed runtime context, lifecycle callbacks — this is the 6.0-introduced replacement for the older `Experimental_Agent`) and **`WorkflowAgent`** (new in `@ai-sdk/workflow`) for durable, long-running agents: "execution state is persisted to durable storage between steps, so agents survive deploys, process restarts, interruptions, and delayed approvals."
- **Timeout budgets (new):** text-generation/agent APIs can now define total, per-step, per-chunk, default-tool, and per-tool timeout budgets natively.
- **Resumable streams:** the 7.0 docs describe "durable, resumable sessions" for agents and "approval replay behavior" for UI flows (interrupted-turn continuation, tool-approval resumption) as part of the `WorkflowAgent`/durable-execution model, distinct from the community `resumable-stream` package pattern described next.

**Is the `resumable-stream` + Redis pattern still current?** Yes — as of the 2026-09-02 access date this remains the documented approach for resuming a dropped `useChat`/`streamText` HTTP stream: the official `vercel/resumable-stream` package (source: https://github.com/vercel/resumable-stream, discovered via WebSearch, not independently WebFetch-verified against a version/date due to search-budget exhaustion — **treat the "still current" claim as NOT INDEPENDENTLY VERIFIED against a dated first-party source**, though it is corroborated by multiple 2026 third-party integration posts, e.g. Upstash's and Ably's, describing it as "the standard for resumable AI chat" as of mid-2026) uses Redis to persist stream chunks so a client can re-attach after a disconnect; community sources note "different npm install versions needed for AI SDK v6 and v7," implying the pattern itself is intact across the v6->v7 boundary but the exact installed variant must match the AI SDK major in use.

**Structured-output guarantees per provider:** **NOT VERIFIED** in depth — general AI SDK behavior (both 6.x and 7.x per the migration guide) is that `generateText`/`streamText` with an `output` setting (schema-constrained generation) delegate to each provider's native structured-output/JSON-mode capability where available and fall back to prompt-engineered JSON + repair otherwise; the SDK does not itself claim a single uniform guarantee across all providers (i.e., strictness/reliability of schema conformance still varies by which underlying provider API is used) — this needs a dedicated read of https://ai-sdk.dev/docs/ai-sdk-core/generating-structured-data for a StateNour-specific verdict per @ai-sdk/anthropic vs @ai-sdk/openai vs @ai-sdk/google, which was not completed in this pass.

## SECTION: Prisma — Q4 (6.x client + 7.x adapter support, Prisma 7 changes, pgvector)

**Current stable major:** **Prisma ORM v7 is GA** (source: https://www.prisma.io/docs/orm/v7/more/releases, accessed 2026-09-02, confirms three maturity tiers — Early Access, Preview, GA — with v7 as the documented current stable line). **Prisma 8 is already at Release Candidate** (`8.0.0-rc.12` at access time) and, unusually, **the npm `latest` dist-tag on the `prisma` package now points at that RC** — confirmed directly via `https://registry.npmjs.org/prisma/latest` returning `"version": "8.0.0-rc.12"` (accessed 2026-09-02) and corroborated by third-party release trackers describing "the first release on the v8 release-candidate line with versions numbered `8.0.0-rc.N` instead of `0.x` minors." Practical consequence: **a bare `npm install prisma@latest` today installs a pre-GA release candidate**, not the stable v7 line — anyone pinning off "latest" without a version floor should pin explicitly to a 7.x range instead. Prisma 8 is being GA'd database-by-database: PostgreSQL support was the first targeted for GA (May-July 2026 timeframe per Prisma's own roadmap post), MongoDB is Early Access, MySQL later — so even once "8" starts appearing as genuinely GA for Postgres, it is a newer, actively-stabilizing line, not a settled target to jump to immediately.

**Is a 6.x `@prisma/client` with a 7.x `@prisma/adapter-neon` a supported combination?** **NOT DIRECTLY CONFIRMED** — no first-party Prisma documentation page found that explicitly blesses or forbids mixing a v6 client with a v7 adapter package (checked https://www.prisma.io/docs/guides/upgrade-prisma-orm/v7, accessed 2026-09-02, which covers the 6->7 upgrade as a unified jump, not a mix-and-match scenario). What IS confirmed from that same page: **Prisma 7 made driver adapters mandatory for all databases** ("The way to create a new Prisma Client has changed to require a driver adapter for all databases... In Prisma ORM 7, driver adapters are required when using the query compiler"), and driver-adapter connection-pool defaults changed to match the underlying JS driver instead of Prisma's own v6 defaults (example given: `pg`'s adapter has no connection timeout by default, `0`, versus Prisma v6's built-in 5-second timeout) — so even where a 6-client-plus-7-adapter combination happens to install and run, StateNour should not assume v6-era pool-timeout behavior still holds; that alone is a reason to treat the current pin (`prisma ^6.3.1` client + `@prisma/adapter-neon ^7.6.0`) as a **mismatched pair to resolve deliberately** (either hold the adapter back to a 6.x release or upgrade the client to 7.x to match), rather than something to leave as-is on the assumption it's a supported skew. **Verdict: this pairing is unverified/likely-unsupported and should be aligned to the same major on both sides.**

**Prisma 7 breaking changes vs 6** (same source, accessed 2026-09-02): ESM required (`"type": "module"` in `package.json`); schema `provider` moves from `prisma-client-js` to `prisma-client`; generator block's `output` path is now **required** (no more implicit default `@prisma/client` import path — custom generated-client import paths replace it); environment variables are no longer auto-loaded (must load explicitly, e.g. via `dotenv`); `prisma db seed` must be invoked explicitly (no more implicit auto-seed); the Metrics preview feature is removed entirely; Client middleware (`$use`) is removed, replaced by the Client Extensions API; CLI flags `--skip-generate`/`--skip-seed` are gone; connection-pool defaults differ from v6 (see above).

**pgvector support status:** **not natively supported in Prisma 7** (or 6). Source: https://www.prisma.io/docs/postgres/database/postgres-extensions (accessed 2026-09-02): "Prisma ORM doesn't natively support all extension types yet. For extensions that introduce custom types (like `vector` from pgvector), you can use customized migrations and raw SQL or TypedSQL to work with them" — the supported pattern is: create the extension via a raw-SQL migration, represent the column as `Unsupported("vector")` in the Prisma schema, and query exclusively through `$queryRaw`/`$executeRaw` (Prisma Studio cannot render these columns — "Queries against those tables will return a deserialization error"). **Native pgvector support is arriving specifically in Prisma 8**, not 7: Prisma's own August 2026 update describes "the first four extensions on the new Prisma 8 extension API: pgvector, arktype-json, ParadeDB, and CipherStash" (source: WebSearch-discovered Prisma blog/changelog content, not independently WebFetch-verified line-by-line — treat the Prisma-8-ships-native-pgvector claim as **highly likely but not fully first-party-confirmed** in this pass). If StateNour needs first-class vector-column support without the raw-SQL workaround, that motivates an eventual Prisma 8 migration (once GA for Postgres) rather than anything available in the currently-pinned 6.x/7.x combination.

**Known issues with `trustHost: true`:** confirmed via multiple open first-party GitHub issues (accessed 2026-09-02, all on `nextauthjs/next-auth`), pattern is **configuration-inconsistency bugs**, not a documented CVE-class vulnerability:
- Issue #12176 ("Trust Host not working as expected") and #10915 (subdomain behavior inconsistent between v4 and v5) — `trustHost`/`AUTH_TRUST_HOST` not being honored consistently by the resolved config in some deployment shapes.
- Issue #11452 — `AUTH_TRUST_HOST` **cannot be explicitly set to `false`** to disable it once true; the string value is truthy-parsed such that an explicit `"false"` doesn't actually disable trust-host behavior — a footgun if StateNour ever needs to toggle this off per-environment via env var rather than code.
- Terminology inconsistency flagged across issues: the `trustHost` config option's own docs reference `host`, while `AUTH_TRUST_HOST`'s behavior is actually about trusting the `X-Forwarded-Host` header — i.e., the naming and the documented mechanism don't line up cleanly, a recurring source of misconfiguration reports.
- No first-party advisory (GHSA) specifically tying `trustHost: true` to a host-header-injection CVE was found in this pass — the risk is the generic, well-known one for **any** framework's "trust X-Forwarded-Host" flag: if StateNour's edge/proxy (Railway) does not itself strip or normalize incoming `X-Forwarded-Host` from the original client before it reaches the app, `trustHost: true` will trust whatever host header the app receives, which is a spoofing risk if any untrusted layer sits between the internet and Railway's own proxy. **Action item, not a confirmed live CVE:** verify Railway's edge terminates/sets `X-Forwarded-Host` itself (rather than passing through a client-supplied value) before treating `trustHost: true` as safe in front of Auth.js.

**Version currency:** StateNour pins `@sentry/nextjs 10.73.0`, which is **exactly** the current `latest` dist-tag — confirmed via `https://registry.npmjs.org/@sentry/nextjs/latest` (accessed 2026-09-02, returned `"version": "10.73.0"`). No action needed on version currency.

- **`instrumentation-client.ts`** is the current client-init convention (superseding the older `sentry.client.config.ts` pattern).
- **`withSentryConfig`** wraps `next.config.js`/`.ts` to enable automatic source-map upload and related build-time integration.
- **`Sentry.captureRequestError`**, wired through Next.js's `onRequestError` instrumentation hook, automatically captures unhandled server-side request errors; this requires `@sentry/nextjs >= 8.28.0` and Next.js 15+ (StateNour's 10.73.0 / Next 16.2.11 both clear this floor easily).
- **Turbopack-specific gotcha called out by the community (not a first-party Sentry doc line I could directly verify in this pass):** Next.js 16's Turbopack build reportedly does **not** auto-import `sentry.client.config.ts` the way the older webpack build did — client-side Sentry init may need to move into a Client Component `useEffect`/dynamic-import pattern, or fully onto the newer `instrumentation-client.ts` convention. **Recommend StateNour verify its own client-side Sentry init still fires under Next 16 + Turbopack** (Next 16 makes Turbopack the default bundler — see Next.js section above) rather than assuming the pre-16 setup still auto-wires.
- Deprecated `withSentryConfig` options seen in migration chatter: `disableLogger` and `automaticVercelMonitors` — both reportedly now emit deprecation warnings; **NOT independently confirmed against a first-party changelog line** in this pass.

**What `sendDefaultPii: false` does and does not redact:**
- **Does redact / does NOT send by default:** IP addresses, cookies, and User-Agent-adjacent request identifiers are withheld when `sendDefaultPii` is `false` (this is the setting's entire purpose — it gates automatic PII capture).
- **Does NOT redact / still collected regardless:** whatever the app explicitly and intentionally sends — e.g., `Sentry.setUser()` calls, custom breadcrumbs/tags/context the code adds itself, and (per the AI-integration-specific behavior) baseline execution metadata like model names, token counts, tool names, and step timings for AI SDK spans are collected independent of this flag. **Sentry's own AI-integration telemetry has a separate, more dangerous default that `sendDefaultPii` does NOT govern** — see the `recordInputs`/`recordOutputs` finding under the AI SDK telemetry note below; a team that sets `sendDefaultPii: false` and assumes prompts/completions are therefore safe from Sentry would be wrong.
- **Deprecation notice (important, forward-looking):** `sendDefaultPii` itself is being **deprecated and scheduled for removal in v11 of the JavaScript SDKs**, replaced by a more granular `dataCollection` option that controls data categories individually (source: WebSearch-discovered `blog.sentry.io/datacollection-control-panel/` and `docs.sentry.io/product/agents/privacy/`; not independently re-fetched first-party — **flagged as search-summarized, not line-verified**). StateNour is on 10.73.0 (v10 line), so this doesn't force action today, but the eventual v11 upgrade will require migrating this specific config knob.
- **Related, already-patched advisory:** `GHSA-6465-jgvq-jhgp` — "Sensitive HTTP headers may be inadvertently sent to Sentry when `sendDefaultPii` is set to `true`" (source: https://github.com/getsentry/sentry-javascript/security/advisories/GHSA-6465-jgvq-jhgp, accessed 2026-09-02) — affected `@sentry/nextjs`/`@sentry/node` `>=10.11.0, <10.27.0` (Authorization/Cookie headers leaking into trace-span attributes); fixed in `>=10.27.0`. StateNour's 10.73.0 is well past the fix — **not affected**.

**AI SDK telemetry -> Sentry interaction (cross-cutting with Q10/Q2):** the AI SDK's `recordInputs`/`recordOutputs` telemetry options (see AI SDK section above) default to **on**, meaning full prompt/completion text is attached to OpenTelemetry spans by default whenever `experimental_telemetry`/`telemetry` is enabled — and those spans flow into Sentry (or Langfuse) as configured. This is independent of `sendDefaultPii`. **StateNour-specific action item:** confirm whether `recordInputs`/`recordOutputs` are explicitly disabled anywhere sensitive prompts/completions flow (this was flagged in community discussion as a real production incident pattern for other teams — see AI SDK section).

## SUMMARY (security-critical first, then the Next 16 middleware answer, then major-version gaps)

**Security, ranked by confidence and severity:**

1. **js-yaml is confirmed vulnerable today.** StateNour pins the exact version `5.2.0`. GHSA-pm4m-ph32-ghv5 / CVE-2026-73643 (High) — exponential parsing time in flow collections — affects `>=5.0.0,<=5.2.1`; 5.2.0 sits inside that range. Fixed in **5.2.2** (latest is 5.4.1). This is the single cleanest UPGRADE-NOW finding in the audit: bump js-yaml now.

2. **Next.js's July 2026 security release (9 CVEs, including the middleware/proxy bypass CVE-2026-64642) is fixed exactly at the pinned floor, 16.2.11 — but August 2026 shipped two CRITICAL RCEs** (unauthenticated RCE via AVIF image optimization, shared with `sharp`/`libheif`; unauthenticated RCE on Windows-hosted servers) fixed only in **16.3.3+**. Because the pin is `^16.2.11` (a floor, not an exact pin), whether the deployed build actually has the August fixes depends entirely on the lockfile — that could not be checked from outside the repo. **Action: confirm the resolved `next` version is >=16.3.4 (current latest), not stuck at the 16.2.11 floor.** The Windows RCE is likely moot on Railway's Linux hosting, but the AVIF RCE is not host-OS-gated.

3. **Prisma's client (6.x) and driver adapter (`@prisma/adapter-neon` 7.x) are on different majors**, a combination Prisma's own docs never explicitly bless. Prisma 7 changed connection-pool timeout defaults (e.g., `pg` adapter has no timeout by default, versus Prisma 6's built-in 5s) — a silent behavior change, not merely a version-skew curiosity. Align both to one major.

4. **AI SDK telemetry (`recordInputs`/`recordOutputs`) defaults to ON**, meaning full prompts and completions are attached to OpenTelemetry spans and exported to both Langfuse and Sentry by default whenever telemetry is enabled — independent of Sentry's own `sendDefaultPii` flag, which does not cover this path. This is a documented, recurring cross-ecosystem footgun, not a StateNour-specific guess. Audit every telemetry-enabled call site.

5. `next-auth`'s `trustHost: true` has open first-party GitHub issues about inconsistent enforcement (not a disclosed CVE) — verify Railway's edge sets rather than passes through `X-Forwarded-Host` before trusting it.

**Next.js 16 middleware question, answered directly:** Next 16 does **not** ignore `middleware.ts` — Next's own docs state it "is still available for Edge runtime use cases, but it is deprecated and will be removed in a future version" (no removal version committed). The replacement, `proxy.ts`, runs on the **Node.js runtime** (a real behavioral difference, not just a rename) and ships an official codemod (`npx @next/codemod@canary middleware-to-proxy .`). Not an outage-class P0, but a live, open-ended deprecation worth migrating off proactively.

**Major-version gaps found beyond the two flagged in the brief:** AI SDK `ai` 6->7 (plus all four `@ai-sdk/*` provider packages 3->4); MCP SDK v1 (maintenance-only) -> v2 (new package names, 2026-07-28 stateless spec); TypeScript 5.9 -> 7.0 (skipping 6, the last JS-based release — 7.0 is a Go-native compiler rewrite, not an ordinary bump); ESLint 9->10; Vitest 3->4; ioredis 5->6 (RESP3 default protocol, Node 20+ floor); nanoid 5->6; Stagehand 3->4; and next-auth v5, which is now permanently beta under Auth.js's pivot to Better Auth, with no GA timeline.
