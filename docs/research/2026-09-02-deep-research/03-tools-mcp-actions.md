## 2. TOOL REGISTRY TABLE — legend and header (continues after Section 1; see below)

Class-A verified for all 181 rows: name existence, implementation path:line, and the R/W/E class (derived by reading every `execute()` body in the 13 files under lib/ai/tools/) come directly from this snapshot. "job" is a paraphrase of the tool's own `description` string, not independently verified behavior beyond what the code does.

R/W/E class legend (combine as needed, e.g. "W+M"):
- R = reads statenour's own Prisma DB, or is pure compute over its arguments
- W = writes to statenour's own Prisma DB (BrainMemory/Task/Commitment/etc.)
- X = calls an external/3rd-party API or the nickstire bridge, READ-only (no mutation on the far side)
- M = mutates something OUTSIDE statenour's own DB — sends a message, writes to nickstire, creates a GitHub PR/issue, posts to Instagram, writes a Google Calendar event, queues a device command, renders/spawns a subprocess, calls a paid generation API

Capability-registry id column: every one of the 181 rows resolves to **NONE**. `lib/tools/tool-registry.ts`'s 29 ids are dotted strings (`web.search.verified`, `memory.pin`, `github.create_pr`, …) consumed only by the legacy System B (`lib/ai/nick-agent.ts` action blocks, see Section 1b). No code path maps a camelCase `TOOL_CATALOG` name to one of these ids. This is stated once here rather than 181 times.

Approval-policy column (short codes, see Section 1a/1b for the full argument):
- **none** = `execute()` runs the instant the model calls it; the only possible interception is the blanket `stripMutatingTools()` strip when the turn's `actionPermission==="read"` (non-default) — noted as "(strip-only)" where the tool would actually be caught by that classifier's 3 tripwires (sideEffecting flag / write-category / mutating-verb-prefix)
- **self-gated** = the tool's OWN code implements a real gate independent of any registry (named per-tool)

Idempotent column: "yes (helper)" = uses the shared `withToolIdempotency` (`lib/ai/tools/tool-idempotency.ts`); "yes (bespoke)" = tool-specific dedup/no-op logic; "no" = a retry re-executes the effect; "n/a" = read/compute-only, retries are naturally safe.

Sensitivity: PII = customer/personal-identifying data; OPS-SECRET = credentials/tokens/internal infra; PERSONAL = operator's own health/finance/journal data; BIZ = shop financials/ops, no PII; LOW = none of the above.

Verdict: SN = belongs in StateNour; NICKSTIRE-ADMIN = shop-customer-facing capability that arguably belongs on nickstire.org/admin instead (flagged further in Section 8); OK = fine either way / infrastructure.

 - how a chat tool call actually reaches (or bypasses) the gate

This is the load-bearing finding of the audit. There are two structurally separate action-execution systems in this codebase, and the capability-registry/approval-gate/guardian chain the 2026-09-01 audit checked belongs almost entirely to the one that is dormant in production, not the one the 181 catalog tools use.

## 1. ARCHITECTURE (Section 2's table resumes below Section 1b — reordering artifact from incremental writing, content unaffected)

### 1a. System A - AI SDK v6 native tool-calling (what the 181 TOOL_CATALOG tools are)

- lib/ai/tools.ts:20-36 composes nourTools from 7 domain files (brain, tasks, business, content, social, system, meta - each importing further sub-files: tasks.ts pulls in goals, missions, habits, health, finance, calendar). [A] lib/ai/tools.ts:20-36, lib/ai/tools/tasks.ts:27-32,1467-1474
- app/api/ai/chat/prepare-tools.ts:89-95 calls pruneTools(mode, nourTools, ...) and hands the pruned tool object straight to the AI SDK. Each tool's own execute (defined inline via tool({ execute: async (args) => {...} }), AI SDK "ai" package) is what runs when the model emits a tool call - the AI SDK calls execute directly; nothing in this file wraps it with withGuardian or evaluateToolAction. [A] app/api/ai/chat/prepare-tools.ts:89-95
- Grep across all 13 tool-implementation files (lib/ai/tools/{brain,tasks,business,content,social,system,meta,goals,missions,habits,health,finance,calendar}.ts, 9,055 lines total) for withGuardian|evaluateToolAction|checkApprovalGate|tool-registry|tool-policy returns zero matches. [A] (grep corpus: lib/ai/tools/*.ts; positive control: the identical grep against lib/tools/guardian.ts and lib/ai/nick-agent.ts correctly returns matches, so the pattern is not silently failing)
- The ONLY structural gate on this path is stripMutatingTools() (lib/ai/capability-registry.ts:83-93), and it fires only when actionPermission === "read" (app/api/ai/chat/prepare-tools.ts:172-182). It is a fail-closed allowlist filter on the whole tool SET for the turn (sideEffecting flag OR write-category OR mutating-verb-name-prefix OR not-in-catalog => removed), not a per-call approval workflow. [A] lib/ai/capability-registry.ts:15-24,62-93
- actionPermission defaults to "draft", not "read", when the client omits it (lib/ai/chat/gate.ts:98-100). In "draft" mode stripMutatingTools never runs. [A] lib/ai/chat/gate.ts:89-102
- For "draft" mode, app/api/ai/chat/finalize-system-prompt.ts:381-383 injects nothing - the comment reads "'draft' (default) injects nothing - today's approval-gated behavior", but no code on this path gates anything in draft mode; the claim in that comment is aspirational/stale, not backed by an enforcement call. The only code-level restraint for draft is the model's own compliance with a prose instruction ("Action Language Contract") to describe actions in attempt-tense rather than completion-tense - a wording nudge, not a control. [A] app/api/ai/chat/finalize-system-prompt.ts:380-397 (comment vs. absence of any gate call verified by the same zero-match grep above)
- Net effect: when a chat turn is in the default "draft" mode (or explicit "execute" mode), any of the 181 tools the pruner selects - including every sideEffecting / business_write / comms / personal_write tool - executes the instant the model emits a tool call, with no capability-registry lookup, no owner-approval step, and no receipt gate in the tool's own code path. Whatever safety exists per-tool is whatever that tool's own execute() body happens to implement (see registry table, "approval policy actually applied" column).

### 1b. System B - legacy text-block "Nick Agent" actions (what the 29-capability registry / evaluateToolAction / checkApprovalGate chain actually serves)

- lib/ai/nick-agent.ts:1-24 is a pre-tool-calling-era mechanism: "Nick outputs JSON action blocks, the agent layer executes them... No tool-calling API needed." It defines about a dozen dotted action types (task.create, loop.close, commitment.create, decision.log, score.log, alert.resolve, memory.remember/forget, simulation.run, person.update, habit.toggle, etc.) matching the capability-registry's generateDynamicCapability() prefix table (task|loop|commitment|decision|score|alert|habit|simulation|mission|person|memory|system|shop|google|gmail|telegram|camera|arsenal, lib/tools/tool-registry.ts:622-836). [A]
- parseActions(text) (lib/ai/nick-agent.ts:112-125) regex-extracts fenced "action" JSON blocks or [ACTION: {...}] inline markers from the model's own generated text, and is called from lib/services/chat/deferred-background-work.ts:326, itself invoked from runDeferredBackgroundWork AFTER the chat response has already streamed to the user (lib/services/chat/persist-assistant-turn.ts:549). [A]
- executeActions() (plural, exported, lib/ai/nick-agent.ts:422-433) calls executeAction() (singular) per parsed action, which DOES call checkApprovalGate(type, params) -> evaluateToolAction() -> TOOL_REGISTRY/generateDynamicCapability -> creates a Prisma ApprovalRequest row when a policy requires approval. This is the only place in the whole codebase where the 29-entry capability registry is actually consulted on a live chat-adjacent path. [A] lib/ai/nick-agent.ts:138-196,422-429
- Whether the model ever emits an action block depends on whether ACTION_CATALOG (the prompt text teaching that syntax) is in its system prompt. app/api/ai/chat/augment-final-prompt.ts:49-51: chatLayerPrompt = (provider === "ollama" || provider === "gemini") ? systemPrompt : systemPrompt + "...ACTION_CATALOG..." - ACTION_CATALOG is appended ONLY for the Anthropic provider branch; the Ollama/Gemini branches get the prompt WITHOUT it. [A] app/api/ai/chat/augment-final-prompt.ts:49-66
- Memory index (nourcity-adoption-gates / statenour cron storm entries) records prod's live chat model as Ollama Cloud (OLLAMA_MODEL=minimax-m3); app/api/ai/chat/prepare-tools.ts:222-223 corroborates this ("the chat lane now runs a THINKING model (OLLAMA_MODEL=minimax-m3)"). If that holds at request time, System B is dormant by construction in production - the parser (parseActions) still runs defensively on every turn's output text, but the model was never taught the syntax it looks for. [H - inference from the provider branch plus the cited prior-session memory; this snapshot does not contain a runtime trace proving which provider serves a given request, so "dormant in production" is not independently re-verified here beyond the code branch + memory pointer]
- Net effect: the entire 2026-09-01-audited enforcement chain (29 capabilities, evaluateToolAction, checkApprovalGate, ApprovalRequest rows) gates a legacy, largely-superseded action surface that overlaps in name/purpose with roughly a dozen of the 181 catalog tools (createTask vs task.create, pinMemory vs memory.pin, etc.) and is not wired to the 181-tool AI-SDK dispatch path at all. The "7 externalMutation tools are all owner_required/screenshot_required" fact verified 2026-09-01 is true and consistent - but it describes System B's registry, not a control that intercepts System A's 181 tools.

## 3. THE GAP -- refining "152" into a real number, and can mutating tools be auto-selected

**The premise refined.** 181 catalog tools minus 29 registry capabilities is 152, but that arithmetic assumes every non-registered tool is a write/mutation risk. Reading every `execute()` body (the registry table above) gives the real figure: **57 of 181 tools (31%) perform a genuine local write or an external mutation**; the other 124 are reads or pure compute. All 57 have `capability-registry id = NONE` -- not 152 of them, 57 of them, because the registry's 29 ids are simply never consulted on this dispatch path at all (Section 1a). Positive control: `grep "| lib/ai/tools/" report.md | awk` extraction of the R/W/E column, counted independently from the category-count check above, `57` (script + full list included inline above the registry table's closing line).

**Of those 57, exactly 2 have a real, tool-specific approval gate:** `stageCustomerAlert` and `sendOpportunitySms` (both self-implemented: PENDING `ActionReceipt` + Telegram Approve/Decline buttons, verified end-to-end against the Telegram webhook's `oppsms:approve:<id>` handler in Section 7). One more, `browseAndDo`, has a WEAK self-declared gate (a model-supplied `permission` argument, not cross-checked against the session's real `actionPermission` -- Section 2's browser-tools finding). The remaining 54 execute unconditionally the instant the model calls them, in any turn that is not explicitly `actionPermission:"read"` -- and 6 of those 54 (Section 2's classifier-gap finding) execute even THEN.

**Can the pruner auto-select a mutating tool into a turn's exposed set? Yes, both deterministically and probabilistically, with zero risk-based filtering anywhere in the selection path.** Traced `pruneTools()` (`lib/ai/chat-mode.ts:76-604`) tier by tier:

1. **`CORE_TOOLS`** (`lib/ai/chat-mode.ts:95-113`, 7 names) -- all reads (`classifyThought`, `searchMemories`, `getRecentReflections`, `searchReflections`, `rankNextActions`, `getBlindSpots`, `dailyPulse`). No mutating tool here.
2. **`ACTION_CORE`** (`lib/ai/chat-mode.ts:118`) = `["createTask", "completeTask"]` -- **two write tools are unconditionally attached to every standard/deep-mode turn**, by name, with no condition at all.
3. **Exact tool-name mention** -- if the user's text contains a tool's name verbatim (case-insensitive substring match, `lib/ai/chat-mode.ts:118-124`), it's added. Saying "sendTelegram" or "runPython" in a casual sentence is enough.
4. **Keyword families** (`lib/ai/chat-mode.ts:126-524`, ~35 regex-triggered families) -- e.g. the SMS-staging family (`lib/ai/chat-mode.ts:477-483`) attaches `stageCustomerAlert`, `draftOpportunitySms`, `sendOpportunitySms`, `getTopDecisions` on phrases like "text this customer"; the business family attaches `createQuickQuote`/`triageStaleLead`-adjacent tools on "quote"/"estimate"/"lead" mentions. None of these families consult `riskClass`, `sideEffecting`, or the capability registry -- the ONLY criterion is whether the user's text matched a regex.
5. **Semantic ranking** (`lib/ai/chat-mode.ts:571-585`) -- embedding similarity, again with no risk filter.
6. **Default extras** (`lib/ai/chat-mode.ts:591-599`) -- includes `findCustomer` (the customer-360 PII tool, Section 8) on any turn that only matched core/action-core.

Grepped the entire file for `riskClass`, `sideEffecting`, `approval`, `owner_required`, and `capability` (`lib/ai/chat-mode.ts`): zero matches inside `pruneTools()` itself (2 matches total in the file, both in an unrelated comment at line 477 about `stageCustomerAlert` being "approval-gated" -- true of that ONE tool's own code, not of the pruner). [A] `lib/ai/chat-mode.ts:76-604`

`NICK_TOOL_BUDGET` (`lib/ai/chat-mode.ts:545`, `Math.max(10, Number(process.env.NICK_TOOL_BUDGET) || 24)`) caps the exposed set at 24 by default (floor 10), but the cap is a plain FIFO-by-tier cutoff -- it does not preferentially keep reads over writes; `ACTION_CORE`'s 2 writes are simply guaranteed a slot ahead of everything else because they fill tier 2 before tier 4/5 run.

**Net:** on a default (`"draft"`-permission) turn, the model is essentially always offered `createTask`/`completeTask`, and is very likely to be offered whichever other write tools match the turn's own keywords -- with no capability-registry check, no owner-approval step, and (for 54 of the 57 write/mutation tools) no tool-level gate either. The two well-gated exceptions (`stageCustomerAlert`, `sendOpportunitySms`) show the pattern that keeps this safe in practice: safety here is a property of INDIVIDUAL TOOLS that chose to self-implement a receipt-and-approve flow, not a property of the dispatch pipeline.

## 8. TELEGRAM BOT -- commands and the revenue-decision callback

**Scale:** `app/api/telegram/webhook/route.ts` is 2,215 lines with ~35 slash commands (`/status`, `/schedule`, `/brief`, `/memory`, `/brain`, `/alerts`, `/imagine`, `/dump`, `/task`, `/mit`, `/commit`, `/ask`, `/board`, `/draft`, `/research`, `/remind`, `/goals`, `/predict`, `/search`, `/stats`, `/ig`, `/approve`, `/reject`, `/qa`, `/help`, and more) plus inline `callback_data` button handlers. This audit did not read the file end-to-end (out of proportion to the tool-catalog scope) but DID verify the two highest-consequence flows precisely, since they are the actual approval mechanism behind the customer-SMS and revenue-decision tools documented above:

**1. Customer/opportunity SMS approval (`oppsms:approve|deny:<receiptId>` and the plain `approve:`/`deny:` callback_data, `app/api/telegram/webhook/route.ts:223-420`).** On Approve: re-checks the `ActionReceipt` is still `status:"PENDING"` (blocks double-processing / replayed Telegram webhook retries), zod-validates the stored payload, then calls `queryNick("send_opportunity_sms", {opportunityId, body, idempotencyKey, approvedBy:"nour:telegram"})` -- crossing the bridge to nickstire, which (per `sendOpportunitySms`'s own tool description, corroborated here) enforces consent/caps/quiet-hours/dedupe server-side before actually sending. On success the receipt flips to `SUCCESS` with `executedAt`. On Reject, the receipt flips to `FAILED` with a rejection note. This is a properly closed loop: stage -> human tap -> re-verify -> cross-boundary send -> receipt. [A]

**2. Revenue-decision moves (`app/api/telegram/revenue-decision-callback/route.ts`, a DEDICATED route, separate from the main webhook).** Commands `/approve_N`, `/reject_N`, `/approve_all`, `/reject_all` call `decideMove()`/`decideAllForDate()` (`lib/services/revenue-decision-channel.ts:604-678`), which **only flip a `BrainMemory(category:"revenue_move")` row's `metadata.status` between `pending`/`approved`/`rejected`** -- verified by reading the function body. No SMS, no external API call, no shop mutation happens on approve; these "revenue moves" are cron-drafted RECOMMENDATIONS the operator approves/rejects as a decision log, not auto-executed actions. Auth: constant-time compare of `x-telegram-bot-api-secret-token` against `TELEGRAM_WEBHOOK_SECRET` (`app/api/telegram/revenue-decision-callback/route.ts:48-57`, same `timingSafeEqual` pattern as elsewhere) plus a `TELEGRAM_CHAT_ID` allowlist that silently drops foreign chats. `decideMove` is upsert-safe against Telegram's at-least-once delivery (a duplicate `/approve_1` returns `alreadyDecided:true`, no double-write). [A]

**What the main webhook's other ~30 commands mutate was not individually traced in this audit** -- `/task`, `/mit`, `/commit`, `/remind` etc. almost certainly call into the same Prisma models the catalog tools use (Task/Commitment/etc.), but each command's exact write path was not read line-by-line given the file's size relative to this audit's scope. **NOT VERIFIED**: whether every mutating Telegram command has the same idempotency/audit discipline as the two flows above.

## 9. BOUNDARY DOCTRINE -- tools that arguably don't belong in a personal OS

The codebase already documents and enforces a version of this doctrine in several places -- most explicitly the repeated "v7 cleanup · Apr 28" comments (`lib/ai/tools/business.ts:100-103`, `:151-154`; `lib/ai/tools/content.ts:237-241`) retiring `sendSMS`/`sendBulkSMS`/`triggerFollowUp`/`createPaymentLink`/`generateInvoice` with the stated reason "belongs on nickstire.org/admin (real customer DB, real Twilio creds, real Stripe webhook surface)." Evaluated the five named categories against what this audit actually found in the 181-tool catalog:

**`shop.sendSms` -- the literal TOOL_REGISTRY id names a capability that, as actually built, is more conservative than its name suggests.** `shop.sendSms` (`lib/tools/tool-registry.ts:525-540`, System B) sounds like a direct auto-send. The two REAL catalog tools that reach customer SMS -- `stageCustomerAlert` and `sendOpportunitySms` (Section 2, comms table) -- never send directly; both write a PENDING receipt and require a Telegram tap, with the actual send enforced server-side by nickstire's own consent/cap/quiet-hours/dedupe stack (Section 8). So the CAPABILITY exists on the personal-OS chat surface (a boundary-doctrine concern in principle -- Nick can initiate a customer-facing action from a personal assistant), but the IMPLEMENTATION already routes power away from the personal OS at send-time. Verdict: **present, but well-gated** -- the boundary concern is "why can Nick stage a customer text from chat at all," not "Nick can text customers unsupervised."

**`customer-360` -- present, and this is the clearest boundary-doctrine violation found.** `findCustomer` (`lib/ai/tools/business.ts:285-441`) explicitly builds a narrative "customer 360" (its own instruction field says: `"Present the timeline as a STORY... narrate the customer's journey with the shop"`), aggregating nickstire's `customer_search` (name/phone/email/vehicle/lifetime spend/visit count/LTV band/risk status), BrainMemory notes about that customer, and PersonProfile relationship data into one chat response. It is READ-ONLY (no mutation), but it is real customer PII surfaced through a personal-OS chat interface whose own README/empty-state (per the task's live observation) frames itself around personal productivity, not shop-customer-service. `getPendingRevenueMoves`/`getTopDecisions`/`draftOpportunitySms` all key off the SAME nickstire opportunity-queue customer identities. Verdict: **the strongest "should this exist here" candidate** of the five -- it is a full customer-record lookup tool on a system the operator's own prior code comments repeatedly say should NOT hold customer data ("v7 cleanup: mutating business actions... belong on nickstire.org/admin").

**Tire stock -- verified ABSENT from the 181-tool catalog.** No tool among the 181 read for this audit queries live tire inventory/stock levels (grep corpus: `lib/ai/tools/*.ts`, all 13 files fully read; also grepped `app/api` for `tire.?stock|tireInventory|stock.?level`). A tire-stock-ADJACENT system does exist -- `app/api/system/tire-stock-requests/route.ts` reads `BrainMemory(category:"tire_stock_request")` rows written by `/api/vapi/check-used-tire-stock`, a VOICE AI phone-call integration (a customer calls, an AI agent checks stock, the request gets logged) -- but this is a separate subsystem entirely outside the chat tool catalog: not an AI-SDK tool, not reachable by Nick in conversation, purely a read-only ops-log dashboard route. Verdict: **not present as a catalog-tool boundary violation.**

**Pricing advisory -- present, but read-only strategic advice, not a live pricing control.** `pricingAdvisorySummary` (`lib/ai/tools/business.ts:533-590`) reads a cron-generated `BrainMemory(category:"pricing_advisory")` snapshot and its own description states outright: `"Operator-approval only -- this tool NEVER changes shop pricing."` No `execute()` path in this tool touches a price. Verdict: **weaker boundary concern than customer-360** -- it's closer to a competitive-intelligence briefing than an operational shop-pricing lever; the actual pricing CHANGE (if any) happens elsewhere, unreached from this tool.

**Revenue leaks -- present as multiple read-only analytics tools, no PII beyond aggregate/opportunity-row data.** `getEstimateLeaks` (unconverted-estimate aggregate counts, no customer identity), `getTopDecisions` (nickstire's due-aware opportunity queue, includes masked customer identity per `draftOpportunitySms`'s own description), `getPendingRevenueMoves` (cron-drafted move recommendations). All read-only. Verdict: **shop-ops analytics on a personal assistant** -- a real instance of the boundary being blurred (why does Nour's personal chat need a live revenue-leak dashboard when nickstire.org/admin exists for exactly this), but lower severity than customer-360 since none of these three individually surface a specific customer's contact details.

**Corroborating the task's stated live UI facts** (not independently re-verified in this static snapshot -- grepped `components/` and `app/` for the literal strings "revenue leaks" empty-state text and "CATALOG TOOLS" header and found neither as a literal string, meaning they are either template-generated from `TOOL_COUNT`/dynamic data or live in a file this audit's grep patterns missed): the task brief states the chat empty-state offers "Find the biggest revenue leaks -- Leads, estimates, callbacks" as a preset suggestion, and the chat header reads "181 CATALOG TOOLS." Both are consistent with -- and would be explained by -- the tool inventory this audit found: `getEstimateLeaks`/`getTopDecisions`/`findCustomer`/`getAttentionAlerts` are all real, callable, shop-ops-flavored tools sitting in the same catalog as `getBodyData`/`getSleepTrend`/`pinMemory`, with no UI-level separation between "personal OS" and "shop dashboard" surfaces. **NOT VERIFIED**: the exact source file for the empty-state preset text and the header string (Class I -- not located in this snapshot's `app`/`components` trees by the grep patterns tried).

**Overall assessment for Section 9:** of the five named categories, `customer-360` (`findCustomer`) is the clearest, most concrete violation of a "personal OS" boundary as the operator's own code comments define it elsewhere in this same codebase. `shop.sendSms`-class capabilities exist but are well-gated at send-time. Revenue-leak and pricing-advisory tools are shop-ops analytics that blur the boundary without touching customer PII. Tire stock is not present as a chat-reachable capability at all.

**Finding — browseAndDo's permission argument is self-declared, not session-verified.** `lib/ai/browser/browse-and-do.ts:104,174,276` reads `permission` from the tool CALL's own arguments (`opts.permission ?? "draft"`); nothing in that file or in `lib/ai/tools/meta.ts:272-291` cross-checks it against the actual chat session's `actionPermission` set in `lib/ai/chat/gate.ts`. A model that decides (on its own, or under prompt injection from a page it is browsing) to call `browseAndDo({..., permission: "execute"})` gets the unrestrained branch regardless of what the operator's turn was actually authorized for. This is mitigated by `browseAndDo` carrying `sideEffecting: true` in the catalog, so an explicit `actionPermission:"read"` turn still strips the whole tool from the set before the model can call it at all -- but on the default `"draft"` turn (Section 1a), nothing stops the model from self-escalating to `"execute"` on this one call. [A] `lib/ai/browser/browse-and-do.ts:104,174,276`; [H] severity is bounded by requiring the model itself to choose to escalate, not an external attacker directly controlling the argument.
