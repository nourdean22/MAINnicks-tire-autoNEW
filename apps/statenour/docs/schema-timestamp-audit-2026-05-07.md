## v10.0.461 · revision · false-positive caught

The original v10.0.451 audit flagged `StagedRecoveryItem` as a
"confirmed bug · only updatedAt, no createdAt." On verification
(before shipping the migration · per kaizen's "verify before
declaring done") the model was found to have a domain-specific
creation timestamp (`generatedAt DateTime @default(now())`) that
the script's literal-name regex didn't recognize.

The script's logic is now broader: any DateTime field with
`@default(now())` counts as a creation timestamp regardless of
field name (matching `createdAt` · `generatedAt` · `firedAt` ·
`pingedAt` · `recordedAt` · etc.). Likewise any field with the
`@updatedAt` directive counts as an update timestamp.

Net: the StagedRecoveryItem migration is **CANCELED** · no bug.
3 models that were previously in "domain-specific" (correctly so)
are now classified as "only createdAt-equivalent" — a more honest
description of their schema.

## The 40 "only creation-timestamp" models · classification

These models have a creation timestamp (`createdAt` OR a domain-
specific `@default(now())` field) but no update timestamp. Most
are event-shaped (append-only) where `updatedAt` would be
misleading, but a few are records that genuinely mutate over time
without tracking it.

### Confidently event-shaped · NO action needed

These match obvious immutable-event naming patterns

`*Detection` · `*Replay` · `*Generation` · `*Action`):

That's 29 confidently-event-shaped models (was 26 in the v10.0.451

### Possibly mutable · WORTH MANUAL REVIEW

These don't fit the obvious event-shape naming. May or may not
mutate after creation — needs a 30-second look at the consumers
to decide:

- `MissionLink` · join-table-ish · probably immutable, but verify
  there's no "active/inactive" flag that flips post-creation
- `CommandResolution` · resolution outcome of a command · likely
  set once at resolution time, immutable thereafter
- `WorkResult` · result of a task execution · likely immutable
- `MasteryScore` · scored evaluation · is the score ever revised?
  if yes → needs `updatedAt`
- `BodyTracking` · daily body-state entry · is a day's entry edited
  later? if yes → needs `updatedAt`
- `FinancialSnapshot` · snapshot · "snapshot" name suggests
  immutable, but verify
- `ChatMessage` · already known to mutate post-stream (verifier
  rewrites · guard corrections) — **probably needs `updatedAt`**
- `BrainDump` · raw dump captured from voice/text · is it edited
  later? if yes → needs `updatedAt`
- `Contradiction` · detected contradiction · status field that
  changes (resolved/dismissed/accepted)? if yes → needs `updatedAt`
- `ToolVerbRatio` · running ratio · likely updated each tick →
  **probably needs `updatedAt`**
- `VectorEmbedding` · vector for an entity · re-embedded on edits?
  if yes → needs `updatedAt`

That's 11 "possibly mutable" models flagged for review. Each
one's verdict should be captured in a follow-up migration if the
review confirms `updatedAt` is needed.
