> - Gate, `scripts/people-backfill.ts` shape: dry run by default; `--out` writes an ids-only plan and its token;
>   `--execute --plan-file --token` plus `BACKFILL_EXECUTE=1`, all checked before Prisma loads; a `_bak_` copy per
>   pass in one REPEATABLE READ snapshot; compare-and-swap writes; ids-only receipts in `.completion/` that never
>   overwrite; `--revert <receipt>` behind the same gate. `PASS_CAP` 500 per pass, `--limit` lowers it.
> - Round 1 fixes (manager review of d180583ba1, 11 rulings):
>   - Each link pass stamps its own marker: `Mission.updatedBy = backfill:2026-11-03:orphan` or `...:missions`
>     (28 chars max, the column is VarChar(64)). A revert matches only its own pass, so reverting missions never
>     unlinks an orphan link.
>   - The mission write is a compare-and-swap on everything the plan read: still unlinked, live, not KILLED, and
>     `updatedAt` unchanged (each plan row carries it; a plan file without it is refused). The goal is re-read at
>     execute and must still be active.
>   - Every lost row is listed with its reason (`swap_lost`, `goal_not_active`, `ledger_row_gone`, `no_note`,
>     `snippet_changed`) and the run exits 1. A crash mid-loop still writes the receipt as `aborted`, with the rows
>     written so far, and its path is printed before the first write. A Prisma failure prints its code and its last
>     line, never the call's arguments.
>   - Every run prints one vector-coverage line (mission vectors, goals with a vector in that model, unparsable),
>     and an unparsable or other-model vector has its own reason instead of `no_comparable_embedding`. A goal read
>     at the 50 cap prints a warning. `--out` never overwrites a file that exists.
>   - Known limit (ruled skip): a notes revert does not check that the note still holds the backfill's line; no
>     other writer updates `relationship_ledger.note` today. A second writer would need that check first.
> - Round 2 fix (manager ruling on b175ed4dbd): a revert undoes only the rows its own run wrote (the receipt's
>   `written` list), plus an aborted run's `inFlight` row, whose write may have landed. The marker swap settles it.
>   A receipt still `planned` (the process died before it finished) has no `written` list: its revert writes
>   nothing, prints "receipt never finished", and exits 1. A lost note keeps its inner reason
>   (`no_note:already_noted`, ...). A second run of the same pass is already refused at the backup step while its
>   `_bak_` table exists (`CREATE TABLE` on a fixed name, `lib/services/people/backfill-apply.ts:158`); the
>   written-only revert covers a re-run after that table is dropped.
