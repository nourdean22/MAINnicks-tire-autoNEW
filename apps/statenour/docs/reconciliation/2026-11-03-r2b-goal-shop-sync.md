> ## 2026-11-03 · Business goals fill themselves from the shop every night, as a value only (job 2026-11-02-nour-os-interconnect R2b) · 1 ship
>
> Nour, 2026-11-03 10:08 EST: "audit them if not upgrade them too". The R1 audit found no writer that moves a goal from shop numbers, though `LifeGoal.domain` and `LifeGoal.metric` already declare the number and the bridge already returns it.
>
> - **What runs.** `app/api/cron/goal-shop-sync` (folded into mega-evening, 03:00Z, after the shop's day; `config/crons.ts` row, `EVENING_JOBS` entry) calls `syncGoalsFromShop` in `lib/services/goal-shop-sync.ts`. It reads active, live, `kind: metric` goals with domain business (case-insensitive) and a metric of `revenue` or `cars`. Revenue = the bridge `revenue_range` `totalDollars` (rounded to cents), cars = its `invoiceCount` (a counter invoice is a closed job; payment status means nothing).
> - **Window.** ET shop days, both inclusive, as `revenue_range` reads them. The end is `goalDue` (`lib/brain/goal-pace.ts`): a deadline Nour set, otherwise the end of the horizon period the goal was created in, capped at today, so a goal past its period keeps its period's number instead of counting on (and cannot flip to achieved off a longer window). The start is the first day of the period the goal was created in for any DAY..YEAR horizon, with or without a deadline (the weekly review's Extend writes one, and the start must not jump to the creation day), and the creation day otherwise.
> - **Value only.** The write goes through `updateGoal`, which gains an optional second argument `{ source, progressPayload }`: the audit row, the `progress_logged` event and an `achieved` event now say `shop-bridge`, and the event carries the window and the raw read. Every other caller is unchanged (default source `api:goals.PATCH`). No check-in is ever written: a check-in would turn "check-in due" green without Nour looking (manager ruling). A value equal to the current one writes nothing.
> - **Never a zero from a miss.** The bridge read has the Home card's 3 s deadline (`SHOP_READ_DEADLINE_MS`, `lib/home/shop-today.ts`). A transport error, a handler error inside a 200, a rejected fetch, a slow shop or an answer with no number skips the goal as `skipped: bridge unavailable (<reason>)`; after the first timeout the remaining windows skip without another read (3 s each would pass maxDuration). Zero invoices in the window skips too (a quiet window and a stalled shop sync read the same), and so does a total of 0 or less (`updateGoal` would floor a negative total to a written 0). A business goal whose metric is not revenue, cars or reviews ("monthly revenue") is untouched and skipped with that reason. A bridge miss, a zero-invoice window of 7+ days (a sync stall) or a failed write files the run `partial` with the counts and first reason (cron_job_logs keeps status and error, not the result body).
> - **Nour's own progress stays his.** "Goals lifted today" (`lib/services/today-compound.ts` and its legacy REST route) and "loops this week" (`getProgressInWindow`) exclude source `shop-bridge` through `OWN_PROGRESS_WHERE` in `lib/brain/goal-events.ts`, with an explicit NULL branch because SQL `<>` drops a NULL source. The value sparkline keeps shop deltas.
> - **Reviews: recognised, always skipped, on purpose.** The brief named `getReviewStats` total. That total counts the review rows stored from Google Places pulls, which return at most 5 reviews each (`lib/integrations/google-reviews.ts`, `app/api/cron/ingest-reviews`), so it is not the shop's Google review count and writing it would set a wrong number as measured. A reviews goal is skipped with that reason until the bridge has a review-total query.
