## Summary

PSI mobile score went 46 → 86 mid-day after we enabled `prerender-to-all-users` (removing the `isBot()` gate from `prerender-middleware`). Real user browsers then requested asset URLs that were referenced in the prerendered HTML but had been hash-regenerated by the most recent Railway build · 100% asset reference mismatch · browsers received `text/html` (the catch-all `app.use("*")` falling back to `index.html`) when requesting `*.css` / `*.js` files. Refused to apply HTML as CSS/JS · site rendered unstyled with no JavaScript. ~30 minutes of degradation before revert. Defensive 404-on-missing-assets fix in `8d4da3ac` is now permanent.

## Root cause · 5 whys

**Why did real users see an unstyled site?**
Because their browsers requested CSS/JS files referenced in prerendered HTML, and the server returned an HTML page (200) instead of the asset.

**Why did the server return HTML for asset requests?**
Because the catch-all `app.use("*")` at the end of the Express router matches any path that wasn't handled, including `/assets/*.css` and `/assets/*.js`, and returns the index.html file.

**Why didn't the catch-all match asset paths?**
Because the actual asset files referenced in the prerendered HTML had hash filenames that no longer existed on disk after the most recent Railway build. The asset files DO exist on disk · just under different hash names.

**Why did the prerendered HTML reference stale hash filenames?**
Because `prerender-refresh.yml` only regenerates the prerendered HTML once a week. Asset hashes change every Railway deploy (Vite hashes by content). So the prerendered HTML was 7 days old · referencing 7 builds' worth of stale hashes.

**Why was the staleness not caught before shipping?**
Because the `curl /` test that "validated" the change returned 200 with content · we never tested whether the asset URLs IN that HTML actually resolved. `curl -I` on the referenced asset URLs would have surfaced this immediately.

---

## Contributing factors

1. **Verification gap** · curl-`/` smoke test is not the same as "the page actually renders in a browser." Need an end-to-end smoke that fetches the HTML AND the referenced assets.

2. **Catch-all routing too permissive** · `app.use("*")` falling through to `index.html` was a deliberate SPA-routing choice (any unmatched path = client-side route). But it silently masked the asset-404 failure mode.

3. **Prerender regen on a different cadence than asset hashing** · Vite re-hashes assets every deploy · prerender regen runs weekly. Mismatch is structural.

4. **No CDN-level cache invalidation tied to deploys** · even after the revert, cached HTML kept serving stale references for ~5 min.

5. **PSI optimization felt like the entire goal** · once the 46 → 86 number appeared, confirmation bias kicked in. Test was for the number, not for the working site.

## What we changed

### Immediate (already shipped)

1. **`ca592fe5` revert** · restored the `isBot()` gate · prerender-to-all-users disabled.
2. **`8d4da3ac` defensive root-fix** · catch-all now returns honest 404 with `text/plain` for any path ending in static-asset extensions (`.css/.js/.map/.woff*/.ttf/.svg/.png/.ico/.json/.webp`). If we ever re-enable prerender-to-all-users with stale references, browsers see proper 404s instead of MIME-mismatch errors. Boot-time log also surfaces missing-asset state at startup.

### Lessons applied to subsequent ports

- Wave M (modulepreload cleanup) was tested via `curl --output` + grep for actual modulepreload count, not just `curl -I` status check.
- Wave O (hero readability band) is pure overlay · no asset-reference change · safe by construction.
- Wave P (CAN-SPAM) is server-side only · no static-asset surface.

## What we should change

### Future-proofing the prerender path

If we ever re-enable `prerender-to-all-users` for the PSI win, ONE of three approaches must ship alongside:

**Option A · `PRERENDER_ON_BUILD=true` on Railway** · regen prerender HTML on every deploy. Cost: +3-5 min per Railway build. Safest · prerender HTML always references current asset hashes.

**Option B · Hash-rewriting middleware** · serve-time middleware that reads prerendered HTML, detects asset references, rewrites them to current hashes by reading the build manifest. Cost: ~50 LOC + ongoing maintenance.

**Option C · Stable unhashed asset URLs in prerender HTML** · build prerender HTML with non-hashed asset references (e.g. `/assets/index.css` not `/assets/index-DN898QxG.css`). Requires Vite config change · most elegant but biggest refactor.

Recommendation: **Option A · cheapest path · biggest safety margin.**

### Pre-flight gate for asset-reference changes

Add a CI smoke step that:
1. Fetches `/`
2. Parses all `<script src=>`, `<link rel="stylesheet" href=>`, `<link rel="preload" href=>`, `<link rel="modulepreload" href=>` references
3. HEAD-requests each one · expects 200, not 404, not text/html
4. Fails the build if any asset reference doesn't resolve to its expected content-type

This would have caught the prerender bug before it touched real customers.

### Verify-before-claim discipline

The 46 → 86 PSI bump WAS real · but only matters if the site actually rendered. Future PSI changes get a 3-step verification:
1. PSI score moved (the metric)
2. `curl /` returns 200 with content (the basic check)
3. `curl <asset-url-from-rendered-html>` for each referenced asset returns the expected content-type (the truth check)

Step 3 is the new gate.
