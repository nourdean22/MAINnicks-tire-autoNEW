## Contract gate before selecting a multi-supplier path

PartsTech's currently published API agreement has a material exclusivity clause for an application using its developer API: it requires PartsTech to be the exclusive aftermarket parts and tire catalog/procurement integration in that application; if a desired supplier is not connected, the developer must request the connection in writing; PartsTech has 90 days to communicate a timeline; if PartsTech cannot integrate or the supplier will not cooperate, the agreement describes a waiver for direct integration. See [PartsTech API and Services Agreement](https://partstech.com/api-agreement-terms/), especially sections 3-4 (lines 139-145 on the page).

This agreement appears to govern a signed developer API Order Form; it does **not** by itself prove that an existing shop portal account or unrelated integration has those restrictions. Before the build chooses PartsTech for the CRM, get the actual agreement and written answers on AutoZone, PA/IMC and D&K/Gateway, direct integrations, data retention, fees and waivers. The CRM's must-have is comparing the three named sources, so the architecture must preserve that requirement through approved direct paths or written supplier/aggregator approval. Do not sign, bypass, or infer a waiver.

## Shared counter behavior

1. From a confirmed repair order, send a fitment-specific part/tire search to every enabled provider. Each source returns independently as connected, partial, unavailable, timed out or not configured.
2. Normalize supplier SKU, manufacturer/brand/grade, exact-match evidence, branch, quantity or UNKNOWN, checked time, quote expiry, price, core/deposit/fees, pickup/delivery promise, and supported next actions.
3. Reject fitment and required-by failures first. Compare only valid offers using verified landed cost and actual arrival promise; show “best among connected suppliers that responded.”
4. Keep the estimate's retail price and margin rules separate from supplier cost. Refresh stock and cost before order preview; a change must be reviewed.
5. Let the crew select an offer. Open a supported cart or visible vendor portal; the human checks supplier, account/branch, part, quantity, costs and ETA, then submits. The CRM reconciles supplier confirmation, received quantity, invoice cost, returns, cores and credits back to the RO.
6. Never read browser cookies, scrape private pages, reverse-engineer an undocumented private endpoint, or place an order through an AI/browser worker. A timeout after submit stays UNKNOWN until checked at the supplier.

## CRM integration requirements and data boundaries

These are logical records/actions for the selected core ledger, not instructions to create another database or duplicate ALG. Reuse existing customer, vehicle, estimate and tire-order records where possible.

A documented API is preferred; a documented punchout is equally valid where it keeps the supplier catalog in the vendor's licensed environment. Cart transfer, customer approval, supplier acceptance, receipt and payment are separate events. Split-source fulfillment may need multiple human-reviewed orders; one RO never implies one supplier invoice.

**Money:** use integer minor units and explicit currency/unit, quantity and rounding policy. **Permissions:** counter may search/create an estimate; an authorized purchaser reviews each order; receiving staff record physical count/condition; finance reconciles credits. Supplier wholesale data stays staff-only. Customer approval links contain retail estimate facts, never supplier credentials or confidential wholesale catalog responses. Any AI summary receives only permitted, minimized evidence; no supplier catalog ingestion or model training is assumed.
