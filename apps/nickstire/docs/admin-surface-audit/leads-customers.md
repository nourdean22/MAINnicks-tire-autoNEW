## TOP 5 FIXES (ranked by operator leverage)

1. **CustomersBrief false "zero lapsed · roster is healthy"** while 20+ visible customers are AT RISK / HIGH RISK (live-confirmed). Stale `customers.segment` column drives the brief; fresh churn metrics drive the badges → the two contradict on screen. The "all clear" green line actively misleads the operator. **[FIX-NOW-safe (UI) + OPERATOR-DECISION (data refresh cadence)]**
2. **Urgency badge renders un-clamped score → live `36/5`, `27/5` on Leads** (both Kanban + List views). Garbage display from legacy out-of-range stored `urgencyScore`. **[FIX-NOW-safe]**
3. **Declined "FOLLOW-UP" badge reads as a CTA but means "7d SMS already sent"** — ~20 of 35 live rows show it, operator can't tell which estimates still need first contact. **[FIX-NOW-safe]**
4. **Dispatch "Ready Queue" metric ≠ the "Ready Queue" tab.** Strip computes `active − inProgress` (all non-terminal work minus in-progress); the tab lists only `status="ready_for_bay"`. Two different numbers under the same name. **[FIX-NOW-safe]**
5. **Leads urgency badge color tiers diverge between the two views.** Kanban: `>=4` red / `>=3` amber / else grey. List `UrgencyBadge`: `>=4` / `>=3` / else — same cut points BUT Kanban default is `?? 3` while several code paths assume different defaults; combined with #2 this makes the same lead look different in Kanban vs List. **[FIX-NOW-safe]**

Counts: **19 findings** — 5 CONFIRMED-correctness/staleness · 7 deficit · 5 inconsistency · 2 already-OK-verified. iOS-PWA `window.confirm` scan: **clean** (every destructive path uses `confirmDialog`).

Same class as the prior wave's "due now always 0" enum bug.
